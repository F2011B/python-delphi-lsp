# Python Delphi LSP 2.3 Performance Design

## Goal

Reduce first-use and repeated-command latency on multi-million-line Delphi
workspaces without weakening parser compatibility, deterministic Protocol v2
output, source invalidation, or the bounded-memory contract.

Version 2.2.0 is the fixed comparison baseline. An optimization is included in
2.3.0 only when focused correctness tests, the complete test suite, and a
representative benchmark all pass. Experiments that do not improve the relevant
benchmark are reverted before the release candidate is prepared.

## Measured Baseline

The pinned FPC corpus contains 8,549 `.pas`, `.pp`, and `.inc` files and
4,029,668 lines. The release baseline on the current Mac is:

- workspace/context opening: approximately 5.6 seconds unprofiled;
- navigation prewarming: approximately 30.4 seconds total;
- parallel outline stage: approximately 21.9 seconds with eight workers;
- complete pure-Python DelphiAST unit parsing: 42.7 seconds for 4,421 units;
- retained navigation-cache estimate: 879,614,848 bytes at a 1-GiB budget.

Profiling found:

- workspace selection fingerprints the same state twice and performs about
  2.15 million `lstat` plus 265,000 `resolve` calls;
- the preprocessor consumes about half of full-parser time on the two largest
  files;
- the 6.87-MiB `job_web.pas` navigation shard takes 7.58 seconds unprofiled,
  with conditional preprocessing dominating its profile;
- metrics parse units serially after retaining all source strings;
- relation construction reparses every unit and later scans full edge lists for
  each query;
- OpenCode owns a separate in-memory worker per session/root instead of sharing
  the bounded daemon cache.

Absolute profiler timings are not release thresholds because profiling adds
substantial overhead. Ratios and call counts identify the work to eliminate.

## Architecture

### 1. Stable workspace manifest and revision

`AgentWorkspace` owns the selected project's current revision. Project
selection computes it once and returns the stored value until a filesystem
event marks the manifest dirty.

The manifest stores normalized paths and `(size, mtime_ns)` records. Directory
walking, canonicalization, and snapshots are deduplicated. Watcher events carry
the changed paths into the context instead of merely expiring a timer. A
changed file updates its manifest record and invalidates only its derived
shards; structural directory changes may trigger a full discovery fallback.

### 2. Span-oriented preprocessing

The preprocessor keeps the existing public `PreprocessedSource` contract, but
copies ordinary active and inactive text as spans. Source-map entries are
created once per output line. Comments, directives, strings, includes, and
conditional state transitions remain explicit slow paths.

Outline preprocessing consumes the same conditional scanner but requests
inactive ranges rather than constructing, splitting, and rejoining a second
full-sized source string. Newline and offset preservation remain exact.

### 3. Indexed queries and lazy responses

The registry stores normalized symbol names once and builds exact/prefix search
maps. Relation construction materializes adjacency lists keyed by relation and
target group. Protocol pagination operates on a sized iterable and serializes
only the requested page. Response ordering and cursor totals remain unchanged.

### 4. Content-addressed per-file shards

A versioned cache directory under the existing safe cache root stores immutable
per-file navigation shards. Keys include:

- canonical workspace identity;
- source content digest;
- effective compiler defines and include paths;
- parser/cache schema;
- package version.

Writes use a temporary file plus atomic replace. Loads validate schema, key,
record bounds, and source identity. Corrupt or incompatible records are ignored
and rebuilt. The cache never deserializes executable objects; the on-disk format
contains JSON-compatible primitive records.

The first persistent artifact is the navigation declaration shard because it
accounts for the normal cold-start delay. Metrics summaries and relation edges
may use the same store after their parallel pipelines exist. Full mutable
syntax trees are not persisted in 2.3.0.

OpenCode and the CLI daemon use the same shard store. OpenCode may keep its
session/root worker for transport isolation, but must not rebuild unchanged
navigation shards.

### 5. Parallel metrics and staged relations

Metric workers read one file and return compact `UnitMetrics` data; the parent
performs deterministic project aggregation and dependency coupling. Sources
are streamed rather than retained in one dictionary.

Relation building has a parallel parse/extract stage and a deterministic global
link stage. The final graph stores packed edge records and per-relation
adjacency lists. A single file change rebuilds only that file's parse/extract
shard and relinks affected identities.

### 6. Compact retained structures

Long-lived index data uses string interning and integer identifiers for paths,
unit names, symbol names, signatures, and target IDs. Temporary worker results
are primitive records rather than nested `Symbol` and `Scope` graphs.

The normal semantic API remains object-oriented. Compact records are
materialized into cards or semantic objects only at API boundaries.

## Command Coverage

- `open` and `problems`: stored workspace revision, manifest, and lazy pages;
- `find`, `focus`, and `inspect`: persistent navigation shards and name index;
- `metrics`: streamed parallel unit summaries;
- `trace`: persistent parse/extract shards plus adjacency lists;
- `view` and `index`: span preprocessing, persistent shards, and bounded
  parallel workers;
- OpenCode: persistent per-session transport backed by shared disk shards.

## Memory and Safety

The 80-percent warning remains mandatory. OpenCode must expose the same warning
and budget state as CLI cache consumers.

Disk shards have a separate bounded budget and least-recently-used cleanup.
They never count as retained RAM. Cache paths reject symlinks and unsafe
permissions using the existing metadata rules. Source bodies and full ASTs
remain lazy and evictable.

## Compatibility

- DelphiAST remains the default parser.
- Lark remains a bounded strict-mode fallback only for small sources.
- Target IDs, cursor schema, result ordering, and Protocol v2 fields remain
  stable.
- Python 3.10 through 3.14, Windows, macOS, and Linux remain supported.
- No native extension is required. A later optional native scanner is considered
  only after redundant Python work has been removed and separately benchmarked.

## Acceptance Gates

Every retained phase must pass:

1. a red-green regression test for its behavior;
2. focused parser, cache, worker, and protocol tests;
3. `git diff --check`;
4. the complete test suite outside restrictive socket/process sandboxes;
5. serial-versus-parallel and before-versus-after result equality;
6. a benchmark showing improvement in the phase's target metric.

Release-candidate goals on the pinned corpus are:

- first navigation prewarm at least 25 percent faster than 2.2.0;
- unchanged restart at least 5 times faster through persistent shards;
- no more than 512 MiB retained for the compact navigation registry, or a
  documented compact-mode fallback that remains warm;
- warm `find` and `trace` work proportional to candidates/results rather than
  total symbols/edges;
- no increase in parse failures or high timeouts.

If a goal is not reached, the release notes report the measured result rather
than claiming the projected improvement.

## Non-Goals

- changing Delphi language semantics;
- persisting arbitrary Python objects or full AST graphs;
- unbounded worker counts;
- hiding invalidation errors with stale results;
- making Lark the large-source parser;
- publishing 2.3.0 without explicit user authorization.
